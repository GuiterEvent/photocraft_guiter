執行總和以保持圖塊獨立性，因此它們並不是完全的直接替代品。
沒有夜間`std::simd`、特定於體系結構的指令、新的相依性或
這裡介紹的是`target-cpu=native`。傳遞編解碼器 SIMD 相依性性不
提供一個 Gallery 內核。

[PR #1899](https://github.com/storytold/photocraft/pull/1899) 已運作過濾器
可取消工作執行緒的預覽，對於過時的請求有 150 毫秒的解決延遲。
[PR #2207](https://github.com/storytold/photocraft/pull/2207) 解決了預覽比例問題。
此變更可讓工作人員、代理程式大小、引擎命令和 UI 互動保持不變。

## 演演算法和數值契約

虹膜模糊插入七個高斯等級（零加六個幾何間隔
西格瑪）。這不是射線/磁碟採樣核心。每個等級、盒子半徑、重量、
預乘、非預乘和引腳組合保持不變。

- 準備每個銷釘的中心、旋轉、標準化半徑、指數、羽毛和
  每個圖塊模糊一次。分配失敗改為使用按需準備。
- 引腳標準化邊界正方形之外的點超出了其超橢圓。
  它的衰減已經飽和；跳過那裡的平方根/冪。廣場內，
  使用原始表達式、除法和浮點順序。
- 將交錯的來源樣本複製在一起並就地預乘，如下
  #1524 中的可移植行讀取原理。
- 對於每個非零級別，保留來源的頂部/左側並修剪右側/底部
  到輸出加上該等級的實際三箱範圍。刪除前導行
  或列將更改執行總和取消，尤其是對於 HDR。保管
  開始保留準確的結果；後箝位無法到達輸出。
  Tilt-Shift 和 Field 保留其完整視窗。

沒有額外的圖像大小的快取。預乘窗口、西格瑪圖、
輸出累加器和重複使用等級緩衝區已經存在。電平緩衝器
需要時保留原來的全視窗容量一次，防止排
容量加倍後追加；只是其填滿長度和模糊划痕收縮。
準備好的幾何圖形每個活動圖塊的每個引腳使用 36 個位元組。來源讀取、圖塊大小、
人造絲調度、選擇混合和取消服務保持不變。

`tests_iris_reference.rs`凍結基礎內核。差異測試需要
精確的有限 f32 位元（包括帶符號的零），具有匹配的 NaN 分類。
它們使用 1-6 個色版、RGB/Gray/CMYK/Lab、alpha/no alpha、U8/U16/F32、底片
和 HDR 樣本、極端 HDR 取消、旋轉/平移/各向異性引腳、
圓度和模糊臨界值，羽化 0.998，影像邊緣，裁切輸出，完整
焦點/完全模糊、空白/多個/4096 引腳、退化影像、非有限/極端引腳
欄位、選擇和多種圖塊尺寸。上班前及上班後取消
進步保護泉源。無效的最佳化來源長度/零色版
傳回空的內部結果。公共 API/命令行為保持不變。

## 測量方法

Windows x86_64、AMD Ryzen 7 9700X（8 核心/16 邏輯）、64 GiB RAM、穩定 Rust
1.99.0/LLVM 23.1.1。正常工作區發布設定檔（opt-level 3、精簡 LTO、一
codegen 單元），八名 Rayon 工人。沒有並發的 Cargo 建置或其他任務
在測量過程中安排了基準；普通系統活動仍然存在。

`bench_iris`建構具有不同 alpha 和 alpha 的確定性紋理 RGB 層
HDR F32 值。不包括夾具建構和輸出破壞；來源
讀取、引腳準備、過濾、免選擇表面寫回和修剪
都包括在內。每個案例都有一次不定時的熱身，然後重複完整的呼叫。
未更改的基本可執行檔保留在本機以進行重複比較。使用
基礎修訂版上的相同線束可重現比較。

```powershell
$env:CARGO_TARGET_DIR = 'target/agent-iris-blur'
$env:RAYON_NUM_THREADS = '8'
cargo run --release -p photocraft-algo --example bench_iris -- 6000 4000 3
cargo run --release -p photocraft-algo --example bench_iris -- 6000 6000 3
cargo run --release -p photocraft-algo --example bench_iris -- 1500 1000 5 4
cargo run --release -p photocraft-algo --example bench_iris -- 2000 1334 5
cargo run --release -p photocraft-algo --example bench_iris -- 128 96 5
cargo test --release -p photocraft-algo iris_profile_baseline_stages -- --ignored --nocapture
```

2000×1334 運轉是固定模糊參數下的預覽大小的壓力工作負載。
PhotoCraft實際上將 24 MP 減少了四倍，達到 1500×1000（其係數是
sqrt 的上限（像素/2,500,000））。現有的單獨的1500×1000執行模型
直接過濾代理程式工作負載：頂級文件模糊 15/80/300 變成
3.75/20/75；嵌套的多引腳 JSON 數量保留其現有值。
兩種執行都無法測量代理程式建置、引擎歷史記錄、預覽工作佇列、
合成、GPU 上傳、幀呈現或本機滑桿回應。基線和
候選者始終使用相同的解析度、模糊值和樣本計數。

512×512 輸出圖塊的更改前階段分析，一個旋轉圓形引腳：
幾何 4.3–5.8 毫秒；模糊 15/80/300 時預乘 1.5/3.5/11.7 ms；
每個活躍高斯電平大約 3–9/18–19/87–100 ms。整個內核是
30.8/52.1/208.8 ms（跳過未使用的等級）。這些診斷單塊
數字隔離了計算；下面的端到端結果使用重複執行。

## 重複發布結果

值是中間毫秒（最小–最大），而不是幀時間。執行順序：
基礎 24 MP/壓力/小，候選人 24 MP/壓力/小，基礎 24 MP 再次；
然後基數 36 MP，候選 36 MP，再次基數 36 MP，基本預設代理和候選
預設代理。每個全尺寸基礎柱匯集來自兩個三重複的六個樣本
回合；每個候選人有三個。代理、壓力和小圖像列各有
五個樣本。
在每 24 MP 的情況下，兩個基礎輪的中位數都比候選人慢。
變化是顯而易見的，特別是在較大的代理執行中；這些是當地的
測量，而不是跨機器效能保證。

小=模糊15；中 = 模糊 80，旋轉 27°；大=模糊300。
多重 = 兩個模糊度為 80/40 的銷釘，一個圓度為 65，另一個旋轉了 73°。
聚焦 = 半徑 5×5，模糊 80；模糊 = 腳位中心 x = −5，模糊 80。

## 驗證和限制

演演算法測試：399 項通過，15 項現有/診斷測試被忽略。五朵鳶尾花
差異/取消測試也在發布中通過；他們的分析測試是

Clippy 演演算法通過，警告被拒絕。分層通行證（29 條板條箱）。瓦斯姆
檢查所有必需的板條箱和 HEIF 是否通過；不相關的現有死程式碼警告
保留在 CMS/引擎中。記分卡再生產生相同的內容；沒有預算，
語料庫層、選單奇偶性或清單狀態已變更。`test-corpus --changed`
正確地跳過此僅演演算法變更。指令和 UI 程式碼不變，
因此不會觸發命令panic-hunt 和UI 螢幕截圖檢查。

`cargo xtask perf --quick`成功完成，快速執行其設定
原生 CPU/GPU 範例。其迴歸比較被跳過，因為
簽入基準適用於 Apple M4 Pro，而該機器是 Windows/Ryzen
搭配 Radeon RX 9060 XT。快速模式不強制執行全尺寸預算。
結果本地保留在`target/agent-iris-blur/perf/results.json`中；
上面的虹膜基礎/候選測量提供了這種變化的比較。
最終完整的 wasm 和演演算法格式檢查也通過了。

最終診斷單圖塊參考/候選呼叫（相同的設定檔工作負載，
各一對，不是統計基準）：模糊 15, 31.6 → 25.3 ms；模糊80，
52.9 → 43.1 毫秒；模糊 300, 224.1 → 174.7 毫秒。重複的完全過濾結果
保留用於保留變更的績效證據。

未斷言超出基本實現語意的等效性。私人的
