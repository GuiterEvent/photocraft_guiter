# 自動化安全

自動化是一個特權邊界，因為請求可能導致檔案系統存取、應用程式控制、UI 輸入、首選項變更、渲染和命令執行。

## 目前實現

- 桌面控制項綁定到`127.0.0.1`並且每行使用一個 JSON 請求/回覆。
- 無頭 TCP 拒絕成功綁定的非環回位址。
- 每個桌面控制和無頭 TCP 連線必須在方法分派之前使用 256 位元承載令牌進行驗證。
- 桌面和無頭 TCP 上的編碼請求行限制為 1 MiB，無頭
  JSON-lines stdio 伺服器 (`photocraft-cliserve`) 和 MCP stdio。 MCP 線路限制為
  在 rmcp 的行緩衝區之前強制執行；過大的 MCP 線會關閉該 stdio 會話，因為
  無法安全地解析其請求 ID。活動 TCP 連線數限制為 16，且
  無頭/MCP 批次達到 256 個步驟。
- 功能範圍的自動化檔案以區塊的形式開啟讀取，而不從檔案的保留
  元資料長度。讀取會拒絕超出開啟檔案上觀察到的長度的數據，因此增長
  元資料檢查後無法擴展讀取。大型 PSB 文件沒有固定的自動化文件
  尺寸上限；它們的物化位元組和解碼文件仍然需要可用記憶體。
- JSON 行回覆和編碼的 MCP 工具結果限制為 8 MiB；保留批次回覆
  有一個總預算，並在耗盡時停止後續步驟。無頭 stdio JSON 行
  傳輸強制執行與 TCP 相同的請求/回覆上限。
- 無頭預覽拒絕 2048 像素以上的請求邊緣和以上來源文件
  合成前為 67,108,864 像素。全尺寸請求必須適合邊緣天花板。渲染的
  在進行 Base64 編碼或檔案寫入之前，PNG 的大小限制為 5 MiB。可信任本地 CLI 渲染
  保留其現有行為。
- MCP 網橋限制傳入的回复，並且不會在過大的回復後重試操作
  回覆。傳輸失敗後編輯永遠不會自動重新發送（#1007）；伺服器的
  純讀取工具選擇在新連接上進行一次重試，這沒有任何作用。
螢幕截圖在單獨的尺寸、像素和分配上限下進行解碼
  縮小規模； 5 MiB PNG 限制適用於傳回的影像。
- MCP 通常使用 stdio，可以選擇橋接環回控制 TCP。
- 橋接器和 UI 請求路徑使用逾時。
- 引擎指令預計會拒絕無效參數而不會出現恐慌。
- 遠端檔案系統方法使用單獨授予的讀取和寫入目錄功能。
- 沒有`path`的保存（MCP`doc_save`、`serve``doc.save`、控制色版的`app.save`）
  僅以其自己的格式寫回文件自己的 PSD、PSB 或`.pcraft`文件；任何其他
  save 需要明確的`path`，因此自動化永遠不會壓平或轉換它開啟的檔案。
- 自動化路徑必須是適用根目錄下的相對路徑。絕對路徑，父級
  遍歷、備用分隔符號、Windows 裝置名稱、格式錯誤的元件和連結轉義
  在文件生效之前被拒絕。
- 仍使用環境路徑的引擎指令在自動化邊界處無法關閉。合成的
  UI輸入達到相同的命令策略，自動化觸發的檔案鉤子不執行
  使用者設定的指令碼事件路徑。該策略還涵蓋命令在其上執行的每個命令
  代表自己（一個操作的步驟，`file.automate.conditionalModeChange`執行`image.mode.*`），所以
  允許的命令無法到達被拒絕的命令。
-`prefs.set`在檢查檔案系統承載之前應用引擎的點路徑規範化
  首選項部分，包括帶有前導點或重複點的路徑。它拒絕整體偏好
  更新和那些部分；個人安全偏好鍵仍然可用。
- 透過自動化故意拒絕使用`ui.dialog.apply`應用「首選項」對話方塊。

## 已知限制

- 沒有針對每個用戶端或每個工具的功能；
- 沒有超出檔案系統讀取/寫入權限的通用每個用戶端或每工具功能模型；
- 沒有自動批次應用程式首選項對話方塊；代理可以更改個人安全金鑰
`prefs.set`;
- 沒有特定於應用程式的 JSON 深度策略（serde_json 的解析器具有預設的有限遞歸
  限制）、聚合文件/會話記憶體會計、合成器暫存空間會計、
  或命令持續時間/取消預算；
- 每個接受的 TCP 連線一個執行緒；
- 無結構化安全稽核事件流；
- 桌面螢幕截圖擷取/編碼和文件匯入/匯出沒有特定於自動化的
  營運預算；桌面傳輸限制創建後的回應；
- 昂貴的引擎指令不計入會話預算。

命令狀態更改後可能會發生回覆拒絕。此類錯誤報告表明
操作可能已完成。耗盡批量回應預算將停止後續步驟，包括
當正常命令錯誤允許批次繼續時；它不會回滾先前的編輯。
權威協議參考請參閱【控制協議】(../automation/control-protocol.md)。

## 建議的會話模型

現在，傳輸在方法發現之前根據加密隨機憑證建立經過身份驗證的連線。未來的安全閘道應該會將經過驗證的連線轉變為短暫的、功能範圍內的會話。

其餘功能應該是顯式且可組合的，例如：

```text
DocumentRead
DocumentWrite
UiInspect
UiControl
FilesystemRead (implemented as a root capability)
FilesystemWrite (implemented as a separate root capability)
PreferencesWrite
ApplicationControl
```

名稱和粒度仍然是設計建議。重要的屬性是，用戶端授予的文件檢查不會隱式授予任意文件寫入、指標注入、首選項變更或應用程式關閉。

## 建議的請求預算

網關應強制執行並測試以下有限值：

- 請求位元組和 JSON 巢狀；
- 批次步驟和巢狀/遞歸呼叫；
- 並發連接和每個用戶端的正在進行的請求；
- 渲染尺寸和返回的有效負載位元組；
- 文件像素、解碼位元組和聚合會話記憶體；
- 引擎支援的命令持續時間或取消。

限制應該因穩定錯誤而失敗，在昂貴的工作之前應用，並且只能在安全的全域上限內進行設定。審核事件應擷取會話身分、功能決策、方法/命令 ID、結果、持續時間和編輯路徑句柄，而不是檔案內容、令牌或機密。

## 今天的部署指南

優先選擇 stdio，僅在需要時啟動控制 TCP，授予最窄的讀寫根，使用
私有令牌文件，使偵聽器保持環回，使用權限最低的作業系統帳戶，並隔離
來自敏感文件的不受信任的代理。不要提交或記錄不記名令牌。不要使用隧道或代理
到另一台主機的未加密環回協定。
